DOCPR-2845 Planned v0.2 architecture As of 2026-09-15

Dogen is a guided writing appliance with optional context attachments.

A Technical Author works through three human-facing skills. One deterministic local executable records decisions, protects files, and leaves an inspectable trail. Optional intake, onboarding, and mapping prepare context before the main writing loop.

This is the target architecture, not a claim that every part is shipped. Jira status labels are authoritative; implementation notes only explain what exists in the current worktrees.
Current baseline in merged main

The slim Bash implementation and three-skill workflow are the implemented bridge. Robert Kratky did most of this 21-commit slim rework.

Target v0.2 engine

One Python 3.9-compatible, standard-library-only dogen CLI. Jira still marks the core migration tickets In Progress; the team milestone is October 12.

Human remains the release gate

The tool can draft, record, recover, and verify. A person still reviews, merges, and publishes.

Skills guide the work; Bash scripts enforce the durable gates.

dogen-plan

Runs a one-question-at-a-time Socratic intake, declares one unit, and routes by the author's Diataxis intent.

Skill - conversation

Declares an approved documentation unit

  • Grounds in existing docs and optional .dogen/context/ first.
  • Draws out the reader problem and audience before mechanical fields.
  • Records audience, sources, targets, intent, and a reader-facing outline in .dogen/units/<id>/unit.md.
Calls after explicit approvaldogen-signoff.sh
Why
Freeze the approved plan by recording the SHA-256 of unit.md, plus the current short Git HEAD as provenance.
Gate
dogen-record-draft.sh later refuses when no signoff exists or the current plan hash no longer matches the signed hash.
Durable output
Create .dogen/units/<id>/ledger.md if absent, append the ## signoff row, and create one local commit.
Iron law: no draft can be recorded before a valid signoff.
signed plan

dogen-write

Drafts in the declared format and takes one of two evidence paths before every intent converges on the same recording gate.

Skill - intent branch
Reference / explanation

Author directly from declared sources

Both directions author from the signed unit and declared sources. No mechanical step-evidence walk applies.

  • Reference organizes precise facts for lookup.
  • Explanation builds understanding around concepts and relationships.
  • Source fidelity still matters; only the executable-step gate is skipped.
Tutorial / how-to

Walk the procedure before authoring

Agree and commit an annotated step plan, then capture each step's actual output before writing from curated evidence.

Once per stepdogen-record-step.sh
Proof
Capture output bytes; record their SHA-256 with exit code, verdict, mode, command, and step-text SHA-256.
Checks
Reject malformed evidence and stale evidence whose step-text hash no longer matches the plan.
Result
pass, skipped, and deviated resolve the step. fail is recorded but remains unverified, so drafting stays blocked.
Durable output
Replace the matching ## steps row and create one local commit for that step.
Both branches stage the draft and converge here
Final record for every intentdogen-record-draft.sh
Why
Recheck signoff, enforce actionable evidence, suppress byte-identical redrafts, and preserve WR-03 ledger-before-page ordering.
Order
Append the ## generations row first, then write docs/<target>, then create one local commit.
Durable output
A generation record, the drafted page, and a traceable Dogen-Phase: draft commit.
Exit 1Missing or stale signoff
Exit 2Invalid input or target
Exit 3Identical redraft; no-op
Exit 4Actionable steps absent or unresolved
recorded draft

dogen-review

Surfaces provenance, optionally performs a structured findings review, and records one explicit human verdict.

Skill - human verdict
Record modePresent provenance and capture the reviewer's existing verdict.
Review modeRun the deterministic pre-pass, then assess and verify findings.
Writing approach Source fidelity Completeness Structure fit Clarity

Review-mode findings are numbered F-1, F-2, and so on, with must-fix, should-fix, or nit priority.

Every verdict callsdogen-record-review.sh
Why
The verdict must live in the durable record, never only in conversation.
Accept
Append ## reviews with verdict: accept and seal the current page SHA-256.
Fix / redraft
Require a note and append it to ## steering before recording the verdict in ## reviews.
Durable output
Every verdict creates one local review commit; accept seals the page, while correction verdicts also preserve their steering note.
Accept The dogen loop ends.

The page hash is sealed. A human owns the pull request, merge, and publishing decision.

Fix or redraft Return to dogen-write.

The correction is already durable in steering before another drafting pass begins.

4. The deterministic motor underneath

One stdlib-only Python CLI: dogen

Jira: in progress

A single Python file, standard library only, owns every state transition. Skills guide the conversation; the executable enforces the contract. It consolidates the four-script current baseline summarized in the TL;DR above.

Python 3.9 syntax
no package
no venv
no runtime dependencies
Lifecycle
  • Declare, sign off, steer, draft, edit, review, retire
  • Derive state instead of storing a second state file
Signoff and HITL gates
  • Plan hashes expose stale intent
  • No substantial redraft without recorded human input
Evidence
  • Step text, command, exit code, output digest, bounded excerpt
  • Tool-computed evidence for actionable content
Recovery
  • Pending manifest protects before/after bytes
  • Two-pass resume preserves ambiguous author work
Verification
  • Read-only record, page, and git corroboration checks
  • Honest warnings for squash, drift, and unsupported recovery
Scoped local commits
  • Exactly one local commit per transition
  • Explicit pathspecs; no sweeping git add docs/

5. Visible service record on disk

Everything important remains inspectable in the repository

Target artifacts
.dogen/units/<id>/unit.md

The signed human-readable plan: intent, audience, targets, sources, and body.

.dogen/units/<id>/ledger.jsonl

Append-only canonical JSON events, hash-chained so transitions can be verified.

.dogen/staging/<id>/

Draft inputs, reports, bounded evidence excerpts, and recovery material.

docs/*.md or docs/*.rst

The actual drafted documentation files, including multi-file units.

git log -- Dogen-*

Traceable local commits with unit, phase, sequence, and head trailers.

6. External output boundary

Human review, merge, and publish

Outside dogen

Dogen prepares review-ready local work. A person decides whether it is correct, opens or approves the PR, merges, and publishes.

Sphinx and Read the Docs

Build boundary

The documentation stack remains the publication system. Dogen records or consumes build results; it does not replace Sphinx, RTD, or GitHub review.

Optional QA seam

Extension point

A narrow interface may hand documentation to the separate DOCPR-2822 testing effort. Deep integration is explicitly deferred.

7. Validation and adoption feedback

Prove the loop, then feed findings back into it

Planned and triaged

Acceptance suites, real authoring sessions, install tests, provenance audits, UX comparison, and a four-check independent scorer establish what can honestly be claimed. Multi-file support remains unproven until the reference validation leg passes.
